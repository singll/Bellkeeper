# 通知系统运维说明

> 本文档定义 Matrix Notification Plane 的运行、排障、重试与审计口径。

---

## 1. 日常关注点

通知系统长期运行时，重点关注：
- 队列是否积压
- 某频道是否发送失败激增
- Matrix API 是否返回异常
- 是否出现去重误杀或通知风暴
- 房间绑定是否失效

---

## 2. 运行状态

建议通过 Admin API 暴露：
- 近 1 小时发送总数
- 近 1 小时失败总数
- 各频道发送成功率
- 当前重试中的任务数量
- 死信数量
- 最近失败原因统计

---

## 3. 常见故障

### 3.1 Matrix 发送失败

排查顺序：
1. homeserver 地址与 token 是否有效
2. room 绑定是否存在且激活
3. bot 是否仍在目标房间内
4. 发送内容是否违反格式要求
5. 是否触发平台侧限流

### 3.2 某通知未送达

排查顺序：
1. 调用方是否收到 `queued` 成功响应
2. 是否被 dedupe key 合并
3. 是否命中静默/降噪规则
4. 任务是否在重试或死信队列中
5. 路由绑定是否失效

### 3.3 通知重复

排查顺序：
1. 调用方是否未提供稳定 dedupe key
2. 平台 dedupe window 是否过短
3. 同一事件是否由多个系统重复上报
4. 重试逻辑是否未做幂等保护

---

## 4. 重试原则

- 发送失败不应立即丢弃
- 短暂失败（超时、5xx）应自动重试
- 明确失败（4xx 配置错误、房间不存在）应尽快落死信并告警
- 重放必须可审计

---

## 5. 审计口径

每条通知审计至少记录：
- trace id
- source
- channel
- room
- dedupe key
- severity
- attempts
- final status
- error message

这使得运维人员可以回答：
- 为什么没发到
- 为什么发重了
- 为什么发到了错误房间

---

## 6. 变更原则

- 房间绑定变更必须走治理接口，不手改 hardcode
- 频道语义要稳定，避免频繁改名
- 模板更新后需要保留版本或至少保留变更记录
- 高优先级告警频道的限流策略必须谨慎

---

## 7. 与调用方的协作要求

建议要求 n8n / 运维脚本 / 其他调用方：
- 明确传 `source`
- 明确传 `dedupe_key`
- 采用逻辑频道，不直接传 room id
- 复杂富文本使用 `html`，同时提供降级 `message`

---

## 8. 第一版排障最小集

第一版至少应有：
- 发送记录查询
- 失败记录查询
- 单条任务重放
- 按 channel 查询最近通知
- 按 source 查询最近通知

这样才能真正把通知当作基础设施运维，而不是黑盒发送功能。
